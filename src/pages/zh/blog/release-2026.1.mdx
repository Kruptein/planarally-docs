## 角色卡基础功能

### 为什么

我时不时收到的一个抱怨是缺少角色卡。
我一直认为，制作一个适用于所有系统/用途的通用角色卡并不可行，因此角色卡更适合由 mod 来实现。

话虽如此，mod 仍处于非常实验性的阶段，需要技术知识才能创建，而且说实话，PA 是一款非常小众的 VTT。
因此这个领域一直没有实际工作也就不足为奇了。

我仍然认为，一个好看的「万能」角色卡并不可行，但我尝试创建了一个更基础的系统，并与骰子系统集成。
这样，mod 仍然可以在后台使用这个通用核心系统，同时提供更美观的 UI。

### 实现方式

这个版本在「编辑形状」（edit shape）UI 中新增了一个名为「自定义数据」（custom data）的标签页。

![自定义数据总览](./2026.1/custom-data-overview.png)

你可以在这里自由添加与形状相关的数据，并以树状数据格式组织这些数据。

目前可以添加的数据共有 3 种类型：

- 文本
- 数字
- 骰子表达式

![自定义数据编辑](./2026.1/custom-data-edit.png)

其中大部分都一目了然。骰子表达式的妙处在于，你可以直接用给定的表达式加载骰子工具，表达式可以引用其他自定义数据元素，简称引用（reference）。

![自定义数据骰子表达式](./2026.1/custom-data-dice-expression.png)

此外，你还可以在骰子工具中直接使用这些引用，它会显示一个自动补全 UI，帮助你从正确的形状中选择属性。

![自定义数据骰子上下文](./2026.1/custom-data-dice-context.png)

骰子工具的另一个新增功能是，所选内容中每个带有骰子表达式的形状都会有一个快捷按钮。
这样你就不必反复打开形状设置、切换到自定义数据标签页并点击掷骰按钮来进行所需的掷骰。

![自定义数据骰子宏](./2026.1/custom-data-dice-macro.png)

### 未来规划

目标是更新其他一些地方，让它们也能与引用交互。
跟踪器（Tracker）和光环（aura）是最能从中受益的地方之一。
（例如，与生命值引用关联的 HP 跟踪器）

我另外想做的事情是制作一个真正的系统专属角色卡 mod，作为一个不错的展示。
不过对我而言，这方面存在很大的许可/版权问题。

对于许多系统，官方提供这些内容是不被允许的，或者需要签署合同。
例如 D&D，尽管有 SRD，我在这方面也非常谨慎，因为他们有自己的工具，对其他玩家并不太欢迎。
同样，我联系了 Mothership 团队了解可能性，但得到的回复是目前不允许任何 VTT 集成。
Wildsea 系统非常开放，我实际上已经在示例 mod 仓库中开始了与 wildsea 相关的 mod 工作，但我的一大问题是，该系统其实是我自己完全不用 VTT 的少数系统之一，所以感觉有点滑稽。

所以我不太确定接下来该怎么办，这有点像进退两难的局面：从法律角度我确实做不了太多，但人们似乎又想要集成。

## Notes

在 [2024.1](/zh/blog/release-2024.1) 版本中，引入了对笔记系统的大规模重构。
它为之前存在的一些松散概念增加了统一框架和更好的 UI。

它引入了这样一个概念：笔记要么是全局笔记，可在所有战役中使用，要么是特定于某个战役地点的笔记。
思路是，你通常会有针对特定游戏的笔记（本地）或经常需要的笔记，如属性块（全局）。
你可以切换到本地/全局或同时显示两者，还可以进行一些过滤，例如「只显示当前地点的笔记」。

两年后的现在，是时候重新评估我对这个系统的看法，并改变那些不合理的地方了。

### 当前系统存在的问题

#### 战役笔记

我经常遇到的一个问题是，我会创建大量只与特定地点相关的笔记。
这意味着当我在地点 X 时，我要么看到游戏中每个地点的所有笔记，要么只能看到当前地点的笔记。

这听起来似乎不错，但实际上我也有一些笔记与整个战役相关，并且只与该战役相关。
问题在于，由于每条笔记本质上都与其创建时的地点关联，这些战役级笔记很难找到。
如果你将笔记过滤到当前地点，就再也看不到战役级笔记（除非它们恰好是在当前地点创建的）；如果你不过滤，又会看到海量笔记，难以跟踪任何内容。

活动地点的过滤器还隐藏在额外的菜单后面，导致频繁切换时相当麻烦。

#### 形状笔记

另一个奇怪之处是，由于笔记与其创建时的地点关联，当笔记附加到形状上而该形状被移动到其他地点时，就会出现尴尬的情况。
这导致笔记并不总是出现在正确的位置。

#### 全局笔记

如前所述，全局笔记为一些你可能经常需要的笔记填补了空缺。在我最初的设想中，这主要用于怪物属性块或系统规则集。
后来有人提到，他们有时会有与部分战役相关的笔记，因为相同的 NPC 可能出现在多个战役中。

然而问题在于，全局笔记的访问设置需要更多工作，因为它们不属于特定战役，PA 不知道该建议哪些玩家。
因此你必须手动将每位玩家与每条此类笔记关联，这很快就会变得很麻烦。

#### 地点笔记

最后一个烦人的地方是，由于你只能在「所有地点」和「当前地点」之间选择，任何只想快速查阅的其他地点的笔记，都需要完全切换地点或搜索所有笔记。
后一种方式是否可行，取决于你是否记得标题。

### 有哪些变化

带着这些痛点，这个版本对部分概念进行了改造。

![新的 Notes UI](./2026.1/notes-overview.png)

#### 移除全局/本地

本地-全局的设计最终并没有像我最初预期的那样有效。
现实情况是，笔记的用途差异很大，可能只与 1 个地点相关、与多个战役中的多个地点相关，或者与任何特定战役都无关。

因此，现在更侧重于将特定的战役和/或地点关联到笔记上。
现在创建笔记时，你会先选择其主要目标是战役级、地点特定，还是不需要特别关联，但你仍然可以关联任何其他你想关联的地点。

#### 过滤 UI

搜索/过滤 UI 不再使用令人困惑的首选项面板 + 标签过滤栏，而是改成了一个始终立即可用的活动过滤栏，并允许你显示来自当前未活动地点的笔记。

![Notes 过滤](./2026.1/notes-filter.png)

#### 服务端分页

痛点中没有特别提到的一点是，到目前为止笔记完全在客户端分页。
这意味着当你加载战役时，所有笔记都必须提供给客户端。
这最初便于快速推出可用的版本，但会给启动时间和数据库都增加更多负担，而实际上你通常不会与大多数笔记交互。

现在，笔记只在实际请求时才从服务器获取。

分页 UI 也已移至左下角，并且视觉上更加清晰。

#### 标签

此前可以给任何笔记自由添加标签，但没有真正的 QoL 功能来帮助你管理标签。
由于没有下拉、补全、搜索等任何功能，给新笔记添加标签时，你基本必须记住过去某个标签的确切输入方式。

这个版本改变了这一点：标签现在在单独的数据库集合中妥善管理，而不是作为随意的 JSON 数据附加到笔记上。
这样 UI 就能在笔记编辑详情中显示已有标签，也会出现在过滤 UI 栏中。

## 变体

### 权限修复

_贡献者：Rexy712_

变体形状的访问/权限设置方式导致非 DM 无法更改其中的某些方面。
已完成以下修复：

- 玩家现在可以为他们拥有编辑权限的形状添加变体
- 玩家现在可以切换他们拥有编辑权限的形状的变体
- [技术] 变体的访问权限现在仅基于父形状的权限

### 重构公告

变体目前以相当复杂的方式实现。
每个变体都有一个真实的形状实例，还有一个隐藏的控制形状，负责显示正确的形状并管理所有变体的状态/交互。

这样做的优点是每个变体都可以完全定制成任何样子。所有形状设置对每个变体都是独立的，提供充分的创作自由。

但它也带来了很多缺点。

- 任何应该在变体之间共享的概念都必须重复。任何可能适用于所有变体的更改，都需要对所有变体执行。
    - 例外是跟踪器/光环，为此添加了特殊系统使其可共享。
- 整个代码库必须仅为这个小众概念做额外的逻辑处理，因为形状的管理方式会影响大量交互
    - 这为每个其他功能都增加了额外开销，以便与可能的变体形状良好协作
- 由于它们与绝大多数形状的工作方式差异太大，经常会出现一些微妙的问题

现实是，每个形状的完全创作自由并不值得所有这些麻烦，而且在绝大多数情况下也确实不需要。
变体的核心思想只是能够在一些可能略有不同的素材之间快速切换。

我能想到的实际有用的小差异包括棋子的尺寸、可能的名称不同，以及一些跟踪器/光环。

我打算把多个形状及其之间切换的整个复杂性，缩减为只有 1 个形状。
这 1 个形状将有一个新的标签页来管理变体，你可以在其中添加带图标和名称的新条目。

就是这样。对于跟踪器和光环，这也意味着可以移除特殊的「共享」概念。
我最初的计划是不为跟踪器/光环提供特殊交互，只需让用户在切换变体时按需切换跟踪器/光环。
如果这样最终过于麻烦，我也愿意考虑在新的变体标签页中添加一些跟踪器/光环特有的切换逻辑。

这也意味着整体 UX 将得到改善，因为目前如果你配置了多个变体，无法直接加载某个特定变体。
目前你需要逐个循环切换，这会让所有能看到该形状的玩家暂时看到它们。

<Warning>这将在 2026.2 中更改。如果你对这个更改有任何顾虑或问题，请联系我，以便我们看看能做什么。</Warning>

## 网格吸附修复

_贡献者：Rexy712 和 Craftidore_

对吸附行为进行了一系列修复。

### 键盘交互

键盘移动现在也会吸附到最近的网格单元（在吸附相关的情况下）。
此前没有这样做，导致一些奇怪的情况，例如因为形状在移动途中碰到了墙，就会移出网格。

此外还修复了一个 bug：如果在移动过程中启用了 Select 工具中的 Ruler，键盘移动会使形状移动两次。

### 水平与垂直尺寸

在 [2024.2](/zh/blog/release-2024.2#shape-grid-size) 中，增加了对网格环境中形状尺寸的更多控制。
允许用户指定形状在网格上移动时应以多大的尺寸表现，而不管实际素材的尺寸。
它还会显示 PA 推断的形状尺寸。

这个版本进一步改进了这一点，将尺寸属性拆分为水平和垂直分量（适用于方形网格）。
这修复了形状不规则（例如 2x7）时的一些吸附行为。

## 技术重构

### 数据复制改进

PA 经历了多次技术重构，修复了许多长期存在的问题，这些问题直到做出这些更改之前都无法修复。

具体修改了两件事：

- 客户端中形状中间数据的表示方式
- （形状）模板在数据库中的存储方式

我就不详细说技术细节了，但结果是，以下操作此前都有一系列共同的问题，现在应该都能正常工作：

- 撤销/重做形状删除
- 复制-粘贴形状
- 将模板拖放到游戏桌面上

这 3 个系统都一直存在并且在某种程度上可用，但都无法处理存储在更专门位置中的形状信息。
例如，笔记存储在单独的数据库集合中，导致撤销/重做会忘记笔记与形状的关系，复制-粘贴也同样如此。

新的重构不再需要在各处添加特殊情况，上述 3 个系统实际上无需了解这些细节，就能正常工作。

### 素材模板

#### 存储更改

素材模板是一个不错的系统，允许用户保存与某个素材相关的数据，这样以后将该素材拖放到游戏桌面上时，就会预先填充这些数据。（例如记住一只哥布林的 HP/AC）

除了前面章节提到的问题外，模板还有其他一些问题。
由于它们在数据库中的存储方式，它们不受数据库迁移到新版本的任何影响。

这意味着在早期版本中创建的模板，在新版本中使用时可能无法正常工作。

现在它们将作为普通形状存储在数据库中，既支持自动迁移，也使一些其他内部逻辑更加一致。

#### 素材管理器图标

这不是技术重构，但与素材模板相关。

素材管理器现在会在带有模板数据的素材上显示一个图标。
如果你有多个同名的素材（由于不同的集合等原因），并且不确定为哪个保存了信息，这会很有帮助。

### Pydantic 升级

这是对服务器使用的数据验证库的纯技术性升级。
不过它对数据流有显著影响，尽管玩家应该不会感受到实际变化，但我仍有可能遗漏某些导致服务器出错的情况。

我在这里提到这一点主要是为了服务器管理员，如果他们在服务器日志中看到任何验证错误，请尽快报告这些问题！

## Bug 修复

#### 形状顺序不一致

为确保形状重叠时在视觉上按正确顺序显示，服务器会跟踪每个形状的位置。
在移动形状时，某些形状的位置可能需要调整，因为它们可能上移或下移了。

尽管这在很长一段时间内都运行良好，但如今并没有真正的错误纠正机制，所以如果出于某种原因某处出错，导致顺序中出现空档或重复的位置条目，就可能引发一些奇怪的行为。

不断检查顺序的完整性代价相当高，所以我转而寻找一个可以轻松检查不一致性且不会频繁运行的地方。

从现在起，如果你执行「将形状移到最底层」操作，系统将检查更新的形状数量是否与预期数量相符。
如果不相符，所有形状将被重新定位，并向所有连接的客户端显示通知，说明问题并要求刷新以确保视觉正确。

此外，位置更新查询也从性能角度得到了改进，尽管你可能不会注意到。

## 服务器变更

### 日志记录

_贡献者：nwhansen_

现在可以使用服务器配置来设置日志记录行为。

这允许服务器所有者选择是否保留文件日志，以及各个日志记录器捕获何种严重级别。

更多详情请参阅 [配置文档](/zh/server/management/configuration/#logging)。

<Warning title="服务器配置变更">
    通过这项更改，默认日志仅输出到 stdout，因此不像此版本之前那样有文件日志。

    此外，原本位于配置「general」部分的 "max_log_backups" 和 "max_log_size_in_bytes" 日志设置现在已移至文件日志部分。
    如果你专门配置了这些设置，你的服务器将无法启动！

</Warning>
